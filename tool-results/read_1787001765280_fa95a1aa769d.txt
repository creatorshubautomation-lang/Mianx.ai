     1→     1→# MIANX.AI CORE --- DATA PLATFORM & DATABASE ARCHITECTURE SPECIFICATION v1.0
     2→     2→
     3→     3→**Product:** Mianx.ai\
     4→     4→**Document:** Data Platform & Database Architecture\
     5→     5→**Version:** 1.0\
     6→     6→**Status:** Architecture / Pre-Implementation\
     7→     7→**Purpose:** Define the shared data foundation for Mianx.ai Core and
     8→     8→every current and future Domain OS.
     9→     9→
    10→    10→------------------------------------------------------------------------
    11→    11→
    12→    12→# 1. Purpose
    13→    13→
    14→    14→Mianx.ai is a multi-tenant operating-system platform. Its data
    15→    15→architecture must therefore support:
    16→    16→
    17→    17→-   Multiple organizations
    18→    18→-   Multiple domains
    19→    19→-   Multiple brands
    20→    20→-   Multiple branches/sites
    21→    21→-   Strong tenant isolation
    22→    22→-   Shared Core entities
    23→    23→-   Domain-specific entities
    24→    24→-   AI memory and knowledge
    25→    25→-   Events and workflows
    26→    26→-   Auditability
    27→    27→-   Analytics
    28→    28→-   High operational reliability
    29→    29→
    30→    30→The target foundation is:
    31→    31→
    32→    32→``` text
    33→    33→PostgreSQL
    34→    34→   │
    35→    35→   ├── Core Data
    36→    36→   ├── Tenant Data
    37→    37→   ├── Domain Data
    38→    38→   ├── AI Data
    39→    39→   ├── Workflow/Event Data
    40→    40→   └── Audit Data
    41→    41→
    42→    42→Redis
    43→    43→   ├── Cache
    44→    44→   ├── Rate Limits
    45→    45→   ├── Short-lived State
    46→    46→   └── Coordination
    47→    47→
    48→    48→Object Storage
    49→    49→   ├── Documents
    50→    50→   ├── Images
    51→    51→   ├── Reports
    52→    52→   └── AI Artifacts
    53→    53→```
    54→    54→
    55→    55→------------------------------------------------------------------------
    56→    56→
    57→    57→# 2. Data Constitution
    58→    58→
    59→    59→1.  PostgreSQL is the system of record for transactional business data.
    60→    60→2.  Every tenant-owned record has an explicit organization scope.
    61→    61→3.  Tenant isolation is enforced server-side and at the database layer
    62→    62→    where appropriate.
    63→    63→4.  Domain data must connect to Core organization context.
    64→    64→5.  AI memory must retain tenant/domain scope.
    65→    65→6.  Audit records are append-oriented and tamper-resistant.
    66→    66→7.  Cache is never the source of truth.
    67→    67→8.  Object storage is not the source of relational business truth.
    68→    68→9.  Destructive schema changes require migrations and review.
    69→    69→10. Data access must follow least privilege.
    70→    70→
    71→    71→------------------------------------------------------------------------
    72→    72→

   303→   303→# 11. Tenant Isolation
   304→   304→
   305→   305→Every tenant-owned table should normally include:
   306→   306→
   307→   307→``` text
   308→   308→organization_id
   309→   309→```
   310→   310→
   311→   311→Example:
   312→   312→
   313→   313→``` text
   314→   314→poultry_flocks
   315→   315→ ├── id
   316→   316→ ├── organization_id
   317→   317→ ├── farm_id
   318→   318→ └── ...
   319→   319→```
   320→   320→
   321→   321→Never depend only on application code to remember tenant filtering.
   322→   322→
   323→   323→------------------------------------------------------------------------
   324→   324→
   325→   325→# 12. Row Level Security
   326→   326→
   327→   327→PostgreSQL Row Level Security should be considered a major
   328→   328→defense-in-depth mechanism for tenant data.
   329→   329→
   330→   330→Conceptually:
   331→   331→
   332→   332→``` text
   333→   333→request
   334→   334→ ↓
   335→   335→trusted tenant context
   336→   336→ ↓
   337→   337→PostgreSQL session context
   338→   338→ ↓
   339→   339→RLS policy
   340→   340→ ↓
   341→   341→allowed rows
   342→   342→```
   343→   343→
   344→   344→RLS must be designed carefully with the application authentication
   345→   345→model.
   346→   346→
   347→   347→------------------------------------------------------------------------
   348→   348→
   349→   349→# 13. Cross-Tenant Protection
   350→   350→
   351→   351→The following must be tested:
   352→   352→
   353→   353→``` text
   354→   354→Organization A cannot read B
   355→   355→Organization A cannot update B
   356→   356→Organization A cannot delete B
   357→   357→Organization A cannot infer sensitive B data
   358→   358→Organization A cannot trigger B workflow
   359→   359→Organization A cannot access B files
   360→   360→Organization A cannot access B AI memory
   361→   361→```
   362→   362→
   363→   363→Cross-tenant tests are mandatory.
   364→   364→
   365→   365→------------------------------------------------------------------------
   366→   366→
   367→   367→# 14. Foreign Keys
   368→   368→
   369→   369→Use foreign keys for important relational integrity.
   370→   370→
   371→   371→Examples:
   372→   372→
   373→   373→``` text
   374→   374→poultry_flocks.organization_id
   375→   375→ → organizations.id
   376→   376→
   377→   377→poultry_flocks.farm_id
   378→   378→ → poultry_farms.id
   379→   379→```
   380→   380→
   381→   381→Foreign keys should reflect actual lifecycle rules.
   382→   382→
   383→   383→------------------------------------------------------------------------
   384→   384→
   385→   385→# 15. Delete Strategy
   386→   386→
   387→   387→Not every business record should be physically deleted.
   388→   388→
   389→   389→Use explicit lifecycle states where appropriate:
   390→   390→
   391→   391→``` text
   392→   392→active
   393→   393→inactive
   394→   394→archived
   395→   395→cancelled
   396→   396→deleted
   397→   397→```
   398→   398→
   399→   399→For sensitive/audited business records, prefer controlled archival or
   400→   400→soft-delete semantics where required.
   401→   401→
   402→   402→------------------------------------------------------------------------
   403→   403→
   404→   404→# 16. IDs
   405→   405→
   406→   406→Use a consistent ID strategy across the platform.
   407→   407→
   408→   408→Requirements:
   409→   409→
   410→   410→-   globally safe uniqueness
   411→   411→-   API-safe representation
   412→   412→-   no accidental tenant leakage through sequential IDs
   413→   413→-   predictable indexing behavior
   414→   414→
   415→   415→The exact identifier technology should be standardized before
   416→   416→implementation.
   417→   417→
   418→   418→------------------------------------------------------------------------
   419→   419→
   420→   420→# 17. Timestamps
   421→   421→
   422→   422→Standard timestamps:
   423→   423→
   424→   424→``` text
   425→   425→created_at
   426→   426→updated_at
   427→   427→```
   428→   428→
   429→   429→Use timezone-aware timestamps.
   430→   430→
   431→   431→Business events may additionally require:
   432→   432→
   433→   433→``` text
   434→   434→occurred_at
   435→   435→effective_at
   436→   436→```
   437→   437→
   438→   438→Do not confuse record creation time with business-event time.
   439→   439→
   440→   440→------------------------------------------------------------------------
   441→   441→
   442→   442→# 18. Money
   443→   443→
   444→   444→Never store financial values as floating point.
   445→   445→
   446→   446→Use an exact representation appropriate for the currency model.
   447→   447→
   448→   448→Typical conceptual model:
   449→   449→
   450→   450→``` text
   451→   451→amount
   452→   452→currency
   453→   453→```
   454→   454→
   455→   455→Financial calculations require deterministic rounding rules.
   456→   456→
   457→   457→------------------------------------------------------------------------
   458→   458→

   464→   464→

   469→   469→unit

   541→   541→# 23. Indexing
   542→   542→
   543→   543→Indexes should support actual access patterns.
   544→   544→
   545→   545→Common index candidates:
   546→   546→
   547→   547→``` text
   548→   548→organization_id

   550→   550→organization_id + created_at

   552→   552→```
   553→   553→
   554→   554→Do not index every column automatically.
   555→   555→
   556→   556→------------------------------------------------------------------------
   557→   557→
   558→   558→# 24. Composite Indexes
   559→   559→
   560→   560→Multi-tenant queries often need composite indexes.
   561→   561→
   562→   562→Example:
   563→   563→
   564→   564→``` text

   566→   566→```
   567→   567→
   568→   568→or:
   569→   569→
   570→   570→``` text

   572→   572→```
   573→   573→
   574→   574→Index design should follow real query patterns.
   575→   575→
   576→   576→------------------------------------------------------------------------
   577→   577→
   578→   578→# 25. Unique Constraints
   579→   579→
   580→   580→Tenant-scoped uniqueness should include organization scope.
   581→   581→
   582→   582→Example:
   583→   583→
   584→   584→``` text

   586→   586→```
   587→   587→
   588→   588→rather than globally unique slugs when the product permits the same slug
