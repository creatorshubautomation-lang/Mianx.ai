    55→    55→    authorization.
    56→    56→6.  Cross-tenant queries are prohibited unless explicitly part of
    57→    57→    trusted platform operations.
    58→    58→7.  AI data follows the same tenant and domain boundaries.
    59→    59→8.  Sensitive data is minimized and protected.
    60→    60→9.  Schema changes are migration-controlled.
    61→    61→10. Backups and disaster recovery are part of the architecture, not
    62→    62→    afterthoughts.
    63→    63→
    64→    64→------------------------------------------------------------------------
    65→    65→
    66→    66→# 3. Recommended Core Stack
    67→    67→
    68→    68→Conceptual foundation:
    69→    69→
    70→    70→``` text
    71→    71→PostgreSQL
    72→    72→   ├── Core relational data
    73→    73→   ├── RLS
    74→    74→   ├── Transactions
    75→    75→   ├── JSONB where justified
    76→    76→   ├── Full-text/search capabilities
    77→    77→   └── pgvector where justified
    78→    78→
    79→    79→Redis
    80→    80→   ├── Cache
    81→    81→   ├── Short-lived state
    82→    82→   ├── Rate limiting
    83→    83→   └── Queue/supporting coordination
    84→    84→
    85→    85→Object Storage
    86→    86→   ├── Documents
    87→    87→   ├── Images
    88→    88→   ├── Exports
    89→    89→   └── Large files
    90→    90→
    91→    91→Analytics / Warehouse
    92→    92→   └── Long-term analytical workloads
    93→    93→```
    94→    94→
    95→    95→PostgreSQL remains the system of record for transactional business data.
    96→    96→
    97→    97→Supabase provides managed PostgreSQL plus related services; its current
    98→    98→documentation confirms that each project provides a full PostgreSQL
    99→    99→database, with RLS available as the database-level authorization
   100→   100→mechanism. citeturn0search1turn0search0
   101→   101→
   102→   102→------------------------------------------------------------------------
   103→   103→
   104→   104→# 4. Database Philosophy
   105→   105→
   106→   106→Use PostgreSQL for authoritative transactional state.
   107→   107→
   108→   108→Do not turn PostgreSQL into:
   109→   109→
   110→   110→``` text
   111→   111→temporary cache
   112→   112→large binary-file store
   113→   113→unbounded event archive
   114→   114→uncontrolled AI transcript warehouse
   115→   115→```
   116→   116→
   117→   117→Use specialized storage where it provides a clear operational advantage.
   118→   118→

   208→   208→# 8. Organization
   209→   209→

   212→   212→Conceptual:
   213→   213→
   214→   214→``` text
   215→   215→organizations
   216→   216→ ├── id
   217→   217→ ├── name

   231→   231→

   233→   233→
   234→   234→``` text
   235→   235→User
   236→   236→```

   239→   239→
   240→   240→``` text
   241→   241→Organization Membership
   242→   242→```
   243→   243→
   244→   244→Conceptual:
   245→   245→
   246→   246→``` text
   247→   247→users
   248→   248→organizations
   249→   249→organization_members

   252→   252→Membership contains:
   253→   253→
   254→   254→``` text

   260→   260→
   261→   261→A user may belong to multiple organizations.

   321→   321→

   325→   325→poultry_flocks
   326→   326→poultry_feed_batches

   343→   343→

   345→   345→
   346→   346→``` text
   347→   347→organizations

   349→   349→organization_members
   350→   350→domains
   351→   351→organization_domains
   352→   352→subscriptions
   353→   353→entitlements

   355→   355→integrations
   356→   356→ai_agents
   357→   357→ai_runs
   358→   358→```
   359→   359→
   360→   360→Domain tables:
   361→   361→
   362→   362→``` text
   363→   363→poultry_flocks
   364→   364→poultry_farms
   365→   365→restaurant_orders
   366→   366→retail_products

   372→   372→
   373→   373→# 14. Tenant Isolation Model
   374→   374→
   375→   375→Primary model:
   376→   376→
   377→   377→``` text
   378→   378→organization_id
   379→   379→```
   380→   380→
   381→   381→Every tenant-owned table should either:
   382→   382→
   383→   383→1.  contain `organization_id`, or
   384→   384→2.  have an unambiguous foreign-key path to a table containing
   385→   385→    `organization_id`.
   386→   386→
   387→   387→For high-risk tables, direct organization ownership is preferred.
   388→   388→
   389→   389→------------------------------------------------------------------------
   390→   390→
   391→   391→# 15. Tenant Isolation Enforcement
   392→   392→
   393→   393→Use multiple layers:
   394→   394→
   395→   395→``` text
   396→   396→Frontend
   397→   397→ ↓
   398→   398→API Authorization
   399→   399→ ↓
   400→   400→Service Authorization
   401→   401→ ↓
   402→   402→Data Access Layer
   403→   403→ ↓
   404→   404→PostgreSQL RLS
   405→   405→```
   406→   406→
   407→   407→No single layer should be considered the only protection.
   408→   408→
   409→   409→Supabase's current guidance explicitly recommends RLS for exposed tables
   410→   410→and emphasizes that grants and RLS are separate controls: grants
   411→   411→determine whether a role can reach an object, while RLS determines which
   412→   412→rows are accessible. citeturn0search12turn0search0
   413→   413→
   414→   414→------------------------------------------------------------------------
   415→   415→
   416→   416→# 16. RLS Strategy
   417→   417→
   418→   418→For tables exposed through a client-facing Data API:
   419→   419→
   420→   420→``` text
   421→   421→Enable RLS
   422→   422→+
   423→   423→Create explicit policies
   424→   424→+
   425→   425→Grant least privilege
   426→   426→```
   427→   427→
   428→   428→Supabase currently recommends enabling RLS on tables in exposed schemas
   429→   429→and using policies for row-level authorization.
   430→   430→citeturn0search0turn0search12
   431→   431→
   432→   432→------------------------------------------------------------------------
   433→   433→
   434→   434→# 17. RLS Policy Model
   435→   435→
   436→   436→Conceptually:
   437→   437→
   438→   438→``` text
   439→   439→Authenticated User
   440→   440→       ↓
   441→   441→Organization Membership
   442→   442→       ↓
   443→   443→Organization ID
   444→   444→       ↓
   445→   445→Allowed Resource
   446→   446→```
   447→   447→
   448→   448→Example policy logic:
   449→   449→
   450→   450→``` text
   451→   451→user belongs to organization
   452→   452→AND
   453→   453→row.organization_id = organization
   454→   454→```
   455→   455→
   456→   456→Do not use authentication alone as authorization.
   457→   457→
   458→   458→------------------------------------------------------------------------
   459→   459→
   460→   460→# 18. RLS and UPDATE
   461→   461→
   462→   462→Update authorization must check both:
   463→   463→
   464→   464→``` text
   465→   465→existing row access
   466→   466→+
   467→   467→new row ownership
   468→   468→```
   469→   469→
   470→   470→In PostgreSQL RLS this means using appropriate `USING` and `WITH CHECK`
   471→   471→conditions for updates. Supabase's current RLS guidance explicitly calls
   472→   472→this out. citeturn0search0
   473→   473→
   474→   474→------------------------------------------------------------------------
   475→   475→
   476→   476→# 19. Authorization Data
   477→   477→
   478→   478→Authorization data should come from trusted sources.
   479→   479→
   480→   480→Do not use user-editable profile metadata as the authoritative source
   481→   481→for authorization.
   482→   482→
   483→   483→Supabase specifically warns that user-editable `raw_user_meta_data`
   484→   484→should not be used for authorization decisions; authorization metadata
   485→   485→belongs in trusted application-level data. citeturn18file0
   486→   486→
   487→   487→------------------------------------------------------------------------
   488→   488→
   489→   489→# 20. Service-Level Access
   490→   490→
   491→   491→Backend services may need elevated access for trusted operations.
   492→   492→
   493→   493→Rules:
   494→   494→
   495→   495→``` text
   496→   496→Service access
   497→   497→≠
   498→   498→frontend access
   499→   499→```
   500→   500→
   501→   501→Secrets and service credentials must remain server-side.
   502→   502→
   503→   503→Supabase documents that service-role/secret keys bypass RLS and
   504→   504→therefore must never be exposed in frontend applications.
   505→   505→citeturn0search11
   506→   506→
   507→   507→------------------------------------------------------------------------
   508→   508→
   509→   509→# 21. Database Schema Organization
   510→   510→

   512→   512→
   513→   513→``` text
   514→   514→core
   515→   515→identity
   516→   516→billing
   517→   517→audit
   518→   518→integration
   519→   519→ai
   520→   520→analytics
   521→   521→poultry
   522→   522→restaurant
   523→   523→retail
   524→   524→```
   525→   525→
   526→   526→Whether these become PostgreSQL schemas or naming conventions is an

   528→   528→
   529→   529→------------------------------------------------------------------------
   530→   530→
   531→   531→# 22. IDs
   532→   532→
   533→   533→Use globally unique identifiers.
   534→   534→
   535→   535→Recommended default:
   536→   536→
   537→   537→``` text
   538→   538→UUID
   539→   539→```
   540→   540→
   541→   541→or another collision-resistant identifier strategy.
   542→   542→
   543→   543→Avoid exposing sequential database IDs where they create unnecessary
   544→   544→enumeration risk.
   545→   545→
   546→   546→------------------------------------------------------------------------
   547→   547→
   548→   548→# 23. Foreign Keys
   549→   549→
   550→   550→Use foreign keys for important relational integrity.
   551→   551→
   552→   552→Examples:
   553→   553→
   554→   554→``` text
   555→   555→organization_members.organization_id
   556→   556→→ organizations.id
   557→   557→
   558→   558→poultry_flocks.organization_id
   559→   559→→ organizations.id
   560→   560→```
   561→   561→
   562→   562→Do not rely only on application code for critical referential integrity.
   563→   563→
   564→   564→------------------------------------------------------------------------
   565→   565→
   566→   566→# 24. Delete Strategy
   567→   567→
   568→   568→Do not blindly cascade-delete business data.
   569→   569→
   570→   570→Define per entity:
   571→   571→
   572→   572→``` text
   573→   573→hard delete
   574→   574→soft delete
   575→   575→archive
   576→   576→retention
   577→   577→anonymization
   578→   578→```
   579→   579→
   580→   580→Financial/audit records may require different lifecycle rules from
   581→   581→temporary operational data.
   582→   582→
   583→   583→------------------------------------------------------------------------
   584→   584→
   585→   585→# 25. Timestamps
   586→   586→
   587→   587→Important tables should normally include:
   588→   588→
   589→   589→``` text
   590→   590→created_at
   591→   591→updated_at
   592→   592→```
   593→   593→
   594→   594→Additional lifecycle timestamps may include:
   595→   595→
   596→   596→``` text
   597→   597→deleted_at
   598→   598→archived_at
   599→   599→activated_at
   600→   600→completed_at
   601→   601→```
   602→   602→
   603→   603→Store timestamps consistently in UTC at the persistence layer.
   604→   604→
   605→   605→------------------------------------------------------------------------
   606→   606→
   607→   607→# 26. Concurrency
   608→   608→
   609→   609→Critical business updates should use appropriate concurrency controls.
   610→   610→
   611→   611→Options:
   612→   612→
   613→   613→``` text
   614→   614→transactions
   615→   615→row locks
   616→   616→optimistic versioning
   617→   617→unique constraints
   618→   618→idempotency
   619→   619→```
   620→   620→
   621→   621→Example:
   622→   622→
   623→   623→``` text
   624→   624→inventory update
   625→   625→+
   626→   626→concurrent order
   627→   627→```
   628→   628→
   629→   629→must not silently produce impossible inventory state.
   630→   630→
   631→   631→------------------------------------------------------------------------
   632→   632→
   633→   633→# 27. Transactions
   634→   634→
   635→   635→Use transactions for atomic business changes.
   636→   636→
   637→   637→Example:
   638→   638→
   639→   639→``` text
   640→   640→Create Purchase Request
   641→   641→+
   642→   642→Create Audit Record
   643→   643→+
   644→   644→Create Outbox Event
   645→   645→```
   646→   646→
   647→   647→All can be committed atomically where appropriate.
   648→   648→
   649→   649→------------------------------------------------------------------------
   650→   650→
   651→   651→# 28. JSONB
   652→   652→
   653→   653→JSONB is allowed for:
   654→   654→
   655→   655→``` text
   656→   656→flexible configuration
   657→   657→provider payloads
   658→   658→domain-specific metadata
   659→   659→integration settings
   660→   660→AI metadata
   661→   661→```
   662→   662→
   663→   663→Do not use JSONB as an excuse to avoid modeling stable relational
   664→   664→fields.
   665→   665→
   666→   666→------------------------------------------------------------------------
   667→   667→
   668→   668→# 29. Database Constraints
   669→   669→
   670→   670→Use database constraints for invariants.
   671→   671→
   672→   672→Examples:
   673→   673→
   674→   674→``` text
   675→   675→NOT NULL
   676→   676→UNIQUE
   677→   677→CHECK
   678→   678→FOREIGN KEY
   679→   679→```
   680→   680→
   681→   681→Business invariants that must never be violated should be enforced as
   682→   682→close to the data as practical.
   683→   683→
   684→   684→------------------------------------------------------------------------
   685→   685→
   686→   686→# 30. Indexing
   687→   687→
   688→   688→Index based on actual query patterns.
   689→   689→
   690→   690→Common multi-tenant index:
   691→   691→
   692→   692→``` text
   693→   693→(organization_id, created_at)
   694→   694→```
   695→   695→
   696→   696→Domain examples:
   697→   697→
   698→   698→``` text
   699→   699→(organization_id, farm_id)
   700→   700→(organization_id, status)
   701→   701→(organization_id, branch_id, created_at)
   702→   702→```
   703→   703→
   704→   704→Do not create indexes for every column.
   705→   705→
   706→   706→------------------------------------------------------------------------
   707→   707→
   708→   708→# 31. RLS Performance
   709→   709→
   710→   710→RLS can affect query performance, especially on large tables.
   711→   711→
   712→   712→Design policies and indexes together.
   713→   713→
   714→   714→Supabase's current documentation specifically recommends indexing
   715→   715→columns used by RLS policies and optimizing policy expressions for
   716→   716→performance. citeturn0search0
   717→   717→
   718→   718→------------------------------------------------------------------------
   719→   719→
   720→   720→# 32. Partitioning
   721→   721→
   722→   722→Partition only when data volume and access patterns justify it.
   723→   723→
   724→   724→Potential candidates:
   725→   725→
   726→   726→``` text
   727→   727→high-volume events
   728→   728→telemetry
   729→   729→audit history
   730→   730→transaction history
   731→   731→large time-series data
   732→   732→```
   733→   733→
   734→   734→Partition keys might include:
   735→   735→
   736→   736→``` text
   737→   737→time
   738→   738→organization
   739→   739→domain
   740→   740→```
   741→   741→
   742→   742→Do not partition every table prematurely.
   743→   743→
   744→   744→------------------------------------------------------------------------
   745→   745→
   746→   746→# 33. Read Scaling
   747→   747→
   748→   748→As demand grows:
   749→   749→
   750→   750→``` text
   751→   751→Primary
   752→   752→ ↓
   753→   753→Read Replicas
   754→   754→ ↓
   755→   755→Analytics / Warehouse
   756→   756→```
   757→   757→
   758→   758→Transactional writes remain on the authoritative primary.
   759→   759→
   760→   760→------------------------------------------------------------------------
   761→   761→
   762→   762→# 34. Analytics Boundary
   763→   763→
   764→   764→Do not run heavy analytical workloads against the transactional database
   765→   765→indefinitely.
   766→   766→
   767→   767→Architecture:
   768→   768→
   769→   769→``` text
   770→   770→PostgreSQL
   771→   771→ ↓
   772→   772→CDC / ETL / Events
   773→   773→ ↓
   774→   774→Analytics Store / Warehouse
