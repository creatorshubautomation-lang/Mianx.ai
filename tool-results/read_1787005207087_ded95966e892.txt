     1→# MIANX.AI CORE --- DATA PLATFORM & DATABASE ARCHITECTURE SPECIFICATION v1.0
     2→
     3→**Product:** Mianx.ai\
     4→**Document:** Data Platform & Database Architecture\
     5→**Version:** 1.0\
     6→**Status:** Architecture / Pre-Implementation\
     7→**Purpose:** Define the shared data foundation for Mianx.ai Core and
     8→every current and future Domain OS.
     9→
    10→------------------------------------------------------------------------
    11→
    12→# 1. Purpose
    13→
    14→Mianx.ai is a multi-tenant operating-system platform. Its data
    15→architecture must therefore support:
    16→
    17→-   Multiple organizations
    18→-   Multiple domains
    19→-   Multiple brands
    20→-   Multiple branches/sites
    21→-   Strong tenant isolation
    22→-   Shared Core entities
    23→-   Domain-specific entities
    24→-   AI memory and knowledge
    25→-   Events and workflows
    26→-   Auditability
    27→-   Analytics
    28→-   High operational reliability
    29→
    30→The target foundation is:
    31→
    32→``` text
    33→PostgreSQL
    34→   │
    35→   ├── Core Data
    36→   ├── Tenant Data
    37→   ├── Domain Data
    38→   ├── AI Data
    39→   ├── Workflow/Event Data
    40→   └── Audit Data
    41→
    42→Redis
    43→   ├── Cache
    44→   ├── Rate Limits
    45→   ├── Short-lived State
    46→   └── Coordination
    47→
    48→Object Storage
    49→   ├── Documents
    50→   ├── Images
    51→   ├── Reports
    52→   └── AI Artifacts
    53→```
    54→
    55→------------------------------------------------------------------------
    56→
    57→# 2. Data Constitution
    58→
    59→1.  PostgreSQL is the system of record for transactional business data.
    60→2.  Every tenant-owned record has an explicit organization scope.
    61→3.  Tenant isolation is enforced server-side and at the database layer
    62→    where appropriate.
    63→4.  Domain data must connect to Core organization context.
    64→5.  AI memory must retain tenant/domain scope.
    65→6.  Audit records are append-oriented and tamper-resistant.
    66→7.  Cache is never the source of truth.
    67→8.  Object storage is not the source of relational business truth.
    68→9.  Destructive schema changes require migrations and review.
    69→10. Data access must follow least privilege.
    70→
    71→------------------------------------------------------------------------
    72→
    73→# 3. Logical Architecture
    74→
    75→``` text
    76→                    MIANX DATA PLATFORM
    77→                           │
    78→              ┌────────────┼────────────┐
    79→              │            │            │
    80→           Core DB      Domain DB     AI DB Data
    81→              │            │            │
    82→              └────────────┼────────────┘
    83→                           │
    84→                      PostgreSQL
    85→                           │
    86→          ┌────────────────┼────────────────┐
    87→          │                │                │
    88→        Redis         Object Storage    Analytics
    89→```
    90→
    91→This is a logical separation. Initial implementation may use one
    92→PostgreSQL cluster/database with clear schemas and ownership boundaries.
    93→

    96→# 4. Core vs Domain Data
    97→
    98→## Core data
    99→
   100→Shared across domains:
   101→
   102→``` text
   103→organizations
   104→organization_members
   105→users
   106→roles
   107→permissions
   108→subscriptions
   109→plans
   110→features
   111→integrations
   112→workflow_definitions
   113→workflow_runs
   114→events
   115→audit_logs
   116→notifications
   117→files
   118→```
   119→
   120→## Domain data
   121→
   122→Owned by a domain:
   123→
   124→``` text
   125→poultry_farms
   126→poultry_sheds
   127→poultry_flocks
   128→poultry_feed_records
   129→poultry_health_records
   130→```
   131→
   132→Domain tables must reference Core organization context.
   133→
   134→------------------------------------------------------------------------
   135→
   136→# 5. Organization Hierarchy
   137→
   138→Recommended logical hierarchy:
   139→
   140→``` text
   141→Platform
   142→  ↓
   143→Organization
   144→  ↓
   145→Brand / Business Unit
   146→  ↓
   147→Location / Branch / Site
   148→  ↓
   149→Domain
   150→  ↓
   151→Operational Resources
   152→```
   153→
   154→Not every domain requires every hierarchy level.
   155→
   156→For Poultry:
   157→
   158→``` text
   159→Organization
   160→  ↓
   161→Farm
   162→  ↓
   163→Shed
   164→  ↓
   165→Flock
   166→```
   167→

   174→``` text
   175→organizations
   176→```

   178→Possible fields:
   179→
   180→``` text
   181→id
   182→name
   183→slug
   184→status
   185→timezone
   186→locale
   187→currency
   188→created_at
   189→updated_at
   190→```
   191→
   192→Organization is the primary tenant boundary.
   193→
   194→------------------------------------------------------------------------
   195→
   196→# 7. Organization Membership
   197→
   198→``` text
   199→organization_members
   200→```
   201→
   202→Possible fields:
   203→
   204→``` text
   205→id
   206→organization_id
   207→user_id
   208→status
   209→role_id
   210→created_at
   211→updated_at
   212→```
   213→
   214→A user may belong to multiple organizations.
   215→
   216→Membership determines whether the user may operate inside an
   217→organization.
   218→
   219→------------------------------------------------------------------------
   220→
   221→# 8. Roles and Permissions
   222→
   223→Core authorization entities:
   224→
   225→``` text
   226→roles
   227→permissions
   228→role_permissions
   229→organization_members
   230→```
   231→
   232→Permissions should be granular enough for domains.
   233→
   234→Example:
   235→
   236→``` text
   237→poultry.flock.read
   238→poultry.flock.write
   239→poultry.mortality.write
   240→poultry.purchase.approve
   241→```
   242→
   243→------------------------------------------------------------------------
   244→
   245→# 9. Domain Registration
   246→
   247→Core should know which domains are enabled for an organization.
   248→
   249→Conceptual:
   250→
   251→``` text
   252→organization_domains
   253→```
   254→
   255→Fields:
   256→
   257→``` text
   258→id
   259→organization_id
   260→domain_key
   261→status
   262→configuration
   263→enabled_at
   264→created_at
   265→updated_at
   266→```
   267→
   268→This supports:
   269→
   270→``` text
   271→organization
   272→ ├── poultry = active
   273→ ├── restaurant = inactive
   274→ └── retail = active
   275→```
   276→
   277→------------------------------------------------------------------------
   278→
   279→# 10. Multi-Brand / Multi-Branch
   280→
   281→Optional Core entities:
   282→
   283→``` text
   284→brands
   285→locations
   286→```
   287→
   288→Relationships:
   289→
   290→``` text
   291→organization
   292→ ├── brand A
   293→ │    ├── location 1
   294→ │    └── location 2
   295→ └── brand B
   296→      └── location 3
   297→```
   298→
   299→Domains may use or ignore these layers according to their requirements.
   300→
   301→------------------------------------------------------------------------
   302→
   303→# 11. Tenant Isolation
   304→
   305→Every tenant-owned table should normally include:
   306→
   307→``` text
   308→organization_id
   309→```
   310→
   311→Example:
   312→
   313→``` text
   314→poultry_flocks
   315→ ├── id
   316→ ├── organization_id
   317→ ├── farm_id
   318→ └── ...
   319→```
   320→
   321→Never depend only on application code to remember tenant filtering.
   322→
   323→------------------------------------------------------------------------
   324→
   325→# 12. Row Level Security
   326→
   327→PostgreSQL Row Level Security should be considered a major
   328→defense-in-depth mechanism for tenant data.
   329→
   330→Conceptually:
   331→
   332→``` text
   333→request
   334→ ↓
   335→trusted tenant context
   336→ ↓
   337→PostgreSQL session context
   338→ ↓
   339→RLS policy
   340→ ↓
   341→allowed rows
   342→```
   343→
   344→RLS must be designed carefully with the application authentication
   345→model.
   346→
   347→------------------------------------------------------------------------
   348→
   349→# 13. Cross-Tenant Protection
   350→
   351→The following must be tested:
   352→
   353→``` text
   354→Organization A cannot read B
   355→Organization A cannot update B
   356→Organization A cannot delete B
   357→Organization A cannot infer sensitive B data
   358→Organization A cannot trigger B workflow
   359→Organization A cannot access B files
   360→Organization A cannot access B AI memory
   361→```
   362→
   363→Cross-tenant tests are mandatory.
   364→
   365→------------------------------------------------------------------------
   366→
   367→# 14. Foreign Keys
   368→
   369→Use foreign keys for important relational integrity.
   370→
   371→Examples:
   372→
   373→``` text
   374→poultry_flocks.organization_id
   375→ → organizations.id
   376→
   377→poultry_flocks.farm_id
   378→ → poultry_farms.id
   379→```
   380→
   381→Foreign keys should reflect actual lifecycle rules.
   382→
   383→------------------------------------------------------------------------
   384→
   385→# 15. Delete Strategy
   386→
   387→Not every business record should be physically deleted.
   388→
   389→Use explicit lifecycle states where appropriate:
   390→
   391→``` text
   392→active
   393→inactive
   394→archived
   395→cancelled
   396→deleted
   397→```
   398→
   399→For sensitive/audited business records, prefer controlled archival or
   400→soft-delete semantics where required.
   401→
   402→------------------------------------------------------------------------
   403→
   404→# 16. IDs
   405→
   406→Use a consistent ID strategy across the platform.
   407→
   408→Requirements:
   409→
   410→-   globally safe uniqueness
   411→-   API-safe representation
   412→-   no accidental tenant leakage through sequential IDs
   413→-   predictable indexing behavior
   414→
   415→The exact identifier technology should be standardized before
   416→implementation.
   417→
   418→------------------------------------------------------------------------
   419→
   420→# 17. Timestamps
   421→
   422→Standard timestamps:
   423→
   424→``` text
   425→created_at
   426→updated_at
   427→```
   428→
   429→Use timezone-aware timestamps.
   430→
   431→Business events may additionally require:
   432→
   433→``` text
   434→occurred_at
   435→effective_at
   436→```
   437→
   438→Do not confuse record creation time with business-event time.
   439→
   440→------------------------------------------------------------------------
   441→
   442→# 18. Money
   443→
   444→Never store financial values as floating point.
   445→
   446→Use an exact representation appropriate for the currency model.
   447→
   448→Typical conceptual model:
   449→
   450→``` text
   451→amount
   452→currency
   453→```
   454→
   455→Financial calculations require deterministic rounding rules.
   456→
   457→------------------------------------------------------------------------
   458→
   459→# 19. Units and Measurements
   460→
   461→Domains such as Poultry require explicit units.
   462→
   463→Examples:
   464→
   465→``` text
   466→kg
   467→g
   468→litre
   469→unit
   470→bird
   471→percentage
   472→currency
   473→```
   474→
   475→A value should never be stored without knowing its unit when the unit
   476→affects meaning.
   477→
   478→------------------------------------------------------------------------
   479→
   480→# 20. JSON / Flexible Attributes
   481→
   482→JSON fields can be useful for:
   483→
   484→``` text
   485→configuration
   486→provider metadata
   487→optional domain attributes
   488→AI metadata
   489→integration payloads
   490→```
   491→
   492→Do not use JSON as an excuse to avoid proper relational modeling for
   493→important business entities.
   494→
   495→------------------------------------------------------------------------
   496→
   497→# 21. Prisma Architecture
   498→
   499→Prisma can be used as the application data-access layer.
   500→
   501→Conceptual:
   502→
   503→``` text
   504→Application
   505→    ↓
   506→Domain Service
   507→    ↓
   508→Prisma
   509→    ↓
   510→PostgreSQL
   511→```
   512→
   513→Prisma models should reflect Core and domain ownership clearly.
   514→
   515→------------------------------------------------------------------------
   516→
   517→# 22. Migration Discipline
   518→
   519→Every schema change should use a controlled migration.
   520→
   521→Migration process:
   522→
   523→``` text
   524→Design
   525→ ↓
   526→Migration
   527→ ↓
   528→Review
   529→ ↓
   530→Test
   531→ ↓
   532→Apply
   533→ ↓
   534→Verify
   535→```
   536→
   537→Never make undocumented production schema changes.
   538→
   539→------------------------------------------------------------------------
   540→
   541→# 23. Indexing
   542→
   543→Indexes should support actual access patterns.
   544→
   545→Common index candidates:
   546→
   547→``` text
   548→organization_id
   549→organization_id + status
   550→organization_id + created_at
   551→organization_id + domain_resource_id
   552→```
   553→
   554→Do not index every column automatically.
   555→
   556→------------------------------------------------------------------------
   557→
   558→# 24. Composite Indexes
   559→
   560→Multi-tenant queries often need composite indexes.
   561→
   562→Example:
   563→
   564→``` text
   565→(organization_id, created_at)
   566→```
   567→
   568→or:
   569→
   570→``` text
   571→(organization_id, status, created_at)
   572→```
   573→
   574→Index design should follow real query patterns.
   575→
   576→------------------------------------------------------------------------
   577→
   578→# 25. Unique Constraints
   579→
   580→Tenant-scoped uniqueness should include organization scope.
   581→
   582→Example:
   583→
   584→``` text
   585→UNIQUE (organization_id, slug)
   586→```
   587→
   588→rather than globally unique slugs when the product permits the same slug
   589→in different organizations.
   590→
   591→------------------------------------------------------------------------
   592→
   593→# 26. Audit Data
   594→
   595→Important actions should produce audit records.
   596→
   597→Conceptual:
   598→
   599→``` text
   600→audit_logs
   601→```
   602→
   603→Fields:
   604→
   605→``` text
   606→id
   607→organization_id
   608→actor_type
   609→actor_id
   610→action
   611→resource_type
   612→resource_id
   613→before
   614→after
   615→metadata
   616→request_id
   617→correlation_id
   618→created_at
   619→```
   620→
   621→Avoid storing secrets in audit payloads.
   622→
   623→------------------------------------------------------------------------
   624→
   625→# 27. Event Data
   626→
   627→Event records should support the Event/Workflow Engine.
   628→
   629→Conceptual:
   630→
   631→``` text
   632→events
   633→```
   634→
   635→Fields:
   636→
   637→``` text
   638→id
   639→event_type
   640→event_version
   641→organization_id
   642→source_type
   643→source_id
   644→actor_type
   645→actor_id
   646→correlation_id
   647→causation_id
   648→occurred_at
   649→payload
   650→created_at
   651→```
   652→
   653→Event payloads should follow versioned contracts.
   654→
   655→------------------------------------------------------------------------
   656→
   657→# 28. Outbox Data

   660→
   661→``` text

   687→```
   688→
   689→These records must preserve organization and execution scope.

   691→------------------------------------------------------------------------
   692→
   693→# 30. AI Data

   695→AI-related persistence may include:
   696→
   697→``` text
   698→ai_runs
   699→ai_messages
   700→ai_tool_calls
   701→ai_memory
   702→ai_knowledge_sources
   703→ai_usage
   704→ai_cost_records
   705→```
   706→
   707→All tenant-owned AI data must retain appropriate organization/domain

   709→
   710→------------------------------------------------------------------------
   711→
   712→# 31. AI Memory
   713→
   714→Memory should distinguish:
   715→
   716→``` text
   717→conversation memory
   718→user memory
   719→organization memory
   720→domain memory
   721→operational memory
   722→```
   723→
   724→Not all memory should be globally visible to every agent.
   725→
   726→Access should be governed by authorization and memory scope.
   727→
   728→------------------------------------------------------------------------
   729→
   730→# 32. AI Knowledge
   731→
   732→Knowledge sources may include:
   733→
   734→``` text
   735→documents
   736→policies
   737→manuals
   738→business records
   739→domain knowledge
   740→uploaded files
   741→```
   742→
   743→Knowledge metadata should identify:
   744→
   745→``` text
   746→organization_id
   747→domain_id
   748→source_type
   749→source_id
   750→visibility
   751→version
   752→```
   753→
   754→------------------------------------------------------------------------
   755→
   756→# 33. Vector / Semantic Data
   757→
   758→If semantic search is used, vectors should remain linked to
   759→authoritative source records.
   760→
   761→Conceptual:
   762→
   763→``` text
   764→knowledge_document
   765→      ↓
   766→chunk
   767→      ↓
   768→embedding
   769→      ↓
   770→source reference
   771→```
   772→
   773→A vector result must never become the authoritative business record.
   774→
   775→------------------------------------------------------------------------
   776→
   777→# 34. File / Object Storage
   778→
   779→Use object storage for:
   780→
   781→``` text
   782→images
   783→PDFs
   784→documents
   785→exports
   786→reports
   787→AI-generated artifacts
   788→```
   789→
   790→Store metadata in PostgreSQL.
   791→
   792→Conceptual:
   793→
   794→``` text
   795→files
   796→ ├── id
   797→ ├── organization_id
   798→ ├── storage_key
   799→ ├── mime_type
   800→ ├── size
   801→ └── metadata
   802→```
   803→
   804→------------------------------------------------------------------------
   805→
   806→# 35. File Security
   807→
   808→Files must have:
   809→
   810→``` text
   811→organization scope
   812→access policy
   813→content type validation
   814→size limits
   815→virus/malware scanning where appropriate
   816→signed access URLs where appropriate
   817→retention policy
   818→```
   819→
   820→Never expose unrestricted object-storage buckets for tenant files.
   821→
   822→------------------------------------------------------------------------
   823→
   824→# 36. Redis
   825→
   826→Redis is for short-lived/high-speed operational state.
   827→
   828→Appropriate uses:
   829→
   830→``` text
   831→cache
   832→rate limiting
   833→session-related ephemeral state
   834→distributed coordination
   835→short-lived locks
   836→job coordination
   837→temporary AI state
   838→```
   839→
   840→Redis must not become the permanent system of record.
   841→
   842→------------------------------------------------------------------------
   843→
   844→# 37. Cache Strategy
   845→
   846→Cache entries should have:
   847→
   848→``` text
   849→key
   850→value
   851→TTL
   852→scope
   853→invalidation strategy
   854→```
   855→
   856→Tenant-specific cache keys must include organization context.
   857→
   858→Example:
   859→
   860→``` text
   861→org:{organization_id}:dashboard:{dashboard_id}
   862→```
   863→
   864→------------------------------------------------------------------------
   865→
   866→# 38. Cache Invalidation
   867→
   868→Preferred mechanisms:
   869→
   870→``` text
   871→TTL
   872→explicit invalidation
   873→event-driven invalidation
   874→versioned keys
   875→```
   876→
   877→Never assume cached data is always current.
   878→
   879→------------------------------------------------------------------------
   880→
   881→# 39. Analytics
   882→
   883→Operational PostgreSQL should not necessarily handle every analytical
   884→workload forever.
   885→
   886→Architecture can evolve toward:
   887→
   888→``` text
   889→Operational DB
   890→      ↓
   891→Events / CDC / ETL
   892→      ↓
   893→Analytics Store
   894→      ↓
   895→BI / Reports / AI
   896→```
   897→
   898→Initial scale may allow reporting directly from PostgreSQL with
   899→carefully designed queries.
   900→
   901→------------------------------------------------------------------------
   902→
   903→# 40. Reporting
   904→
   905→Reports should distinguish:
   906→
   907→``` text
   908→operational query
   909→analytical query
   910→generated report
   911→AI-generated insight
   912→```
   913→
   914→AI-generated insights should link back to the data used where feasible.
   915→
   916→------------------------------------------------------------------------
   917→
   918→# 41. Data Retention
   919→
   920→Every data category should eventually have a retention policy.
   921→
   922→Examples:
   923→
   924→``` text
   925→audit
   926→events
   927→workflow runs
   928→AI logs
   929→files
   930→integration logs
   931→analytics data
   932→```
   933→
   934→Retention must consider legal, operational and product requirements.
   935→
   936→------------------------------------------------------------------------
   937→
   938→# 42. Backup
   939→
   940→PostgreSQL backup strategy should include:
   941→
   942→``` text
   943→automated backups
   944→point-in-time recovery where supported
   945→backup monitoring
   946→restore testing
   947→off-site/independent recovery strategy
   948→```
   949→
   950→A backup that has never been restored/tested should not be considered
   951→fully reliable.
   952→
   953→------------------------------------------------------------------------
   954→
   955→# 43. Disaster Recovery
   956→
   957→Define:
   958→
   959→``` text
   960→RPO
   961→RTO
   962→backup frequency
   963→recovery ownership
   964→failover process
   965→restore procedure
   966→```
   967→
   968→Critical Mianx services need explicit recovery objectives.
   969→
   970→------------------------------------------------------------------------
   971→
   972→# 44. Data Encryption
   973→
   974→Protect data:
   975→
   976→``` text
   977→in transit
   978→at rest
   979→in secret storage
   980→```
   981→
   982→Sensitive credentials should use dedicated secret-management mechanisms.
   983→
   984→------------------------------------------------------------------------
   985→
   986→# 45. Database Access
   987→
   988→Use least privilege.
   989→
   990→Different application roles may exist for:
   991→
   992→``` text
   993→application runtime
   994→migration
   995→analytics
   996→background jobs
   997→administration
   998→read-only support
   999→```
  1000→
  1001→Do not use a single unrestricted database credential everywhere.
  1002→
  1003→------------------------------------------------------------------------
  1004→
  1005→# 46. Connection Management
  1006→
  1007→Production database access must account for:
  1008→
  1009→``` text
  1010→connection limits
  1011→pooling
  1012→timeouts
  1013→long-running queries
  1014→transaction duration
  1015→retry behavior
  1016→```
  1017→
  1018→The application should avoid exhausting PostgreSQL connections.
  1019→
  1020→------------------------------------------------------------------------
  1021→
  1022→# 47. Transaction Boundaries
  1023→
  1024→Transactions should be short and intentional.
  1025→
  1026→Example:
  1027→
  1028→``` text
  1029→Validate
  1030→ ↓
  1031→Transaction
  1032→ ├── Business update
  1033→ └── Outbox record
  1034→ ↓
  1035→Commit
  1036→```
  1037→
  1038→Avoid holding database transactions while waiting on external APIs or
  1039→long AI operations.
  1040→
  1041→------------------------------------------------------------------------
  1042→

  1046→transactions.

  1053→Persist intent/job
  1054→ ↓
  1055→Commit
  1056→ ↓
  1057→Worker
  1058→ ↓
  1059→External API
  1060→ ↓
  1061→Persist result
  1062→ ↓

  1064→```
