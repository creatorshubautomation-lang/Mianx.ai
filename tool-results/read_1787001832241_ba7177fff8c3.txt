     1→# MIANX.AI CORE --- DATA PLATFORM, TENANT ISOLATION & DATABASE ARCHITECTURE SPECIFICATION v1.0
     2→
     3→**Product:** Mianx.ai\
     4→**Document:** Data Platform, Tenant Isolation & Database Architecture\
     5→**Version:** 1.0\
     6→**Status:** Architecture / Pre-Implementation\
     7→**Purpose:** Define the shared data foundation for Mianx.ai Core and
     8→every Domain OS, with strong tenant isolation, clear domain boundaries,
     9→scalable PostgreSQL architecture, governed AI data, and operational
    10→resilience.
    11→
    12→------------------------------------------------------------------------
    13→
    14→# 1. Purpose
    15→
    16→Mianx.ai is a multi-tenant, multi-domain SaaS platform.
    17→
    18→The data architecture must support:
    19→
    20→``` text
    21→Mianx Platform
    22→   ↓
    23→Organizations / Tenants
    24→   ↓
    25→Brands / Sites / Branches
    26→   ↓
    27→Domains
    28→   ↓
    29→Domain Modules
    30→   ↓
    31→Business Data
    32→```
    33→
    34→The same foundation must support:
    35→
    36→``` text
    37→Poultry OS
    38→Restaurant OS
    39→Retail OS
    40→Future Domain OSs
    41→```
    42→
    43→without creating a separate database architecture for every domain.
    44→
    45→------------------------------------------------------------------------
    46→
    47→# 2. Data Constitution
    48→
    49→1.  Tenant isolation is a security boundary.
    50→2.  Domain boundaries must be explicit.
    51→3.  Every tenant-owned record must have an enforceable ownership path.
    52→4.  Application authorization and database authorization complement each
    53→    other.
    54→5.  RLS is defense in depth, not a replacement for application
    55→    authorization.
    56→6.  Cross-tenant queries are prohibited unless explicitly part of
    57→    trusted platform operations.
    58→7.  AI data follows the same tenant and domain boundaries.
    59→8.  Sensitive data is minimized and protected.
    60→9.  Schema changes are migration-controlled.
    61→10. Backups and disaster recovery are part of the architecture, not
    62→    afterthoughts.
    63→
    64→------------------------------------------------------------------------
    65→
    66→# 3. Recommended Core Stack
    67→
    68→Conceptual foundation:
    69→
    70→``` text
    71→PostgreSQL
    72→   ├── Core relational data
    73→   ├── RLS
    74→   ├── Transactions
    75→   ├── JSONB where justified
    76→   ├── Full-text/search capabilities
    77→   └── pgvector where justified
    78→
    79→Redis
    80→   ├── Cache
    81→   ├── Short-lived state
    82→   ├── Rate limiting
    83→   └── Queue/supporting coordination
    84→
    85→Object Storage
    86→   ├── Documents
    87→   ├── Images
    88→   ├── Exports
    89→   └── Large files
    90→
    91→Analytics / Warehouse
    92→   └── Long-term analytical workloads
    93→```
    94→
    95→PostgreSQL remains the system of record for transactional business data.
    96→
    97→Supabase provides managed PostgreSQL plus related services; its current
    98→documentation confirms that each project provides a full PostgreSQL
    99→database, with RLS available as the database-level authorization
   100→mechanism. citeturn0search1turn0search0
   101→
   102→------------------------------------------------------------------------
   103→
   104→# 4. Database Philosophy
   105→
   106→Use PostgreSQL for authoritative transactional state.
   107→
   108→Do not turn PostgreSQL into:
   109→
   110→``` text
   111→temporary cache
   112→large binary-file store
   113→unbounded event archive
   114→uncontrolled AI transcript warehouse
   115→```
   116→
   117→Use specialized storage where it provides a clear operational advantage.
   118→

   140→# 6. Physical Database Strategy
   141→
   142→Initial recommendation:
   143→
   144→``` text
   145→One PostgreSQL platform
   146→+
   147→logical isolation by organization/domain
   148→```
   149→
   150→This is simpler and more efficient for the initial multi-tenant SaaS.
   151→
   152→As scale or regulatory requirements grow, selected workloads may move
   153→to:
   154→
   155→``` text
   156→separate database
   157→separate cluster
   158→read replica
   159→warehouse
   160→region-specific deployment
   161→```
   162→
   163→Do not prematurely create one database per customer.
   164→
   165→------------------------------------------------------------------------
   166→
   167→# 7. Tenant Hierarchy
   168→
   169→Recommended hierarchy:
   170→
   171→``` text
   172→Platform
   173→  ↓
   174→Organization
   175→  ↓
   176→Brand
   177→  ↓
   178→Location / Branch / Site
   179→  ↓
   180→Domain
   181→  ↓
   182→Resource
   183→```
   184→
   185→Not every domain needs every hierarchy level.
   186→
   187→For example:
   188→
   189→``` text
   190→Poultry
   191→Organization
   192→ └── Farm
   193→      └── House
   194→           └── Flock
   195→```
   196→
   197→Restaurant:
   198→
   199→``` text
   200→Organization
   201→ └── Brand
   202→      └── Branch
   203→           └── Restaurant Operations
   204→```
   205→
   206→------------------------------------------------------------------------
   207→
   208→# 8. Organization
   209→
   210→Organization is the primary commercial and security tenant.
   211→
   212→Conceptual:
   213→
   214→``` text
   215→organizations
   216→ ├── id
   217→ ├── name
   218→ ├── status
   219→ ├── default_locale
   220→ ├── default_currency
   221→ ├── created_at
   222→ └── updated_at
   223→```
   224→
   225→Every tenant-owned business record should have a reliable path back to
   226→an organization.
   227→
   228→------------------------------------------------------------------------
   229→
   230→# 9. Organization Membership
   231→
   232→Separate:
   233→
   234→``` text
   235→User
   236→```
   237→
   238→from:
   239→
   240→``` text
   241→Organization Membership
   242→```
   243→
   244→Conceptual:
   245→
   246→``` text
   247→users
   248→organizations
   249→organization_members
   250→```
   251→
   252→Membership contains:
   253→
   254→``` text
   255→user_id
   256→organization_id
   257→role
   258→status
   259→```
   260→
   261→A user may belong to multiple organizations.
   262→
   263→------------------------------------------------------------------------
   264→
   265→# 10. Domain Registry
   266→
   267→Mianx Core owns the domain registry.
   268→
   269→Conceptual:
   270→
   271→``` text
   272→domains
   273→ ├── id
   274→ ├── key
   275→ ├── name
   276→ ├── version
   277→ ├── status
   278→ └── configuration
   279→```
   280→
   281→Examples:
   282→
   283→``` text
   284→poultry
   285→restaurant
   286→retail
   287→```
   288→
   289→------------------------------------------------------------------------
   290→
   291→# 11. Organization Domain Activation
   292→
   293→A tenant may activate selected domains.
   294→
   295→``` text
   296→organization_domains
   297→ ├── organization_id
   298→ ├── domain_id
   299→ ├── status
   300→ ├── configuration
   301→ └── activated_at
   302→```
   303→
   304→This connects:
   305→
   306→``` text
   307→Billing
   308→+
   309→Entitlements
   310→+
   311→Domain Access
   312→```
   313→
   314→------------------------------------------------------------------------
   315→
   316→# 12. Domain Data Boundary
   317→
   318→Domain-owned tables should clearly belong to their domain.
   319→
   320→Example:
   321→
   322→``` text
   323→poultry_farms
   324→poultry_houses
   325→poultry_flocks
   326→poultry_feed_batches
   327→```
   328→
   329→Restaurant:
   330→
   331→``` text
   332→restaurant_branches
   333→restaurant_menu_items
   334→restaurant_orders
   335→restaurant_tables
   336→```
   337→
   338→Avoid generic tables that become impossible to reason about.
   339→
   340→------------------------------------------------------------------------
   341→
   342→# 13. Core vs Domain Tables
   343→
   344→Core tables:
   345→
   346→``` text
   347→organizations
   348→users
   349→organization_members
   350→domains
   351→organization_domains
   352→subscriptions
   353→entitlements
   354→audit_logs
   355→integrations
   356→ai_agents
   357→ai_runs
   358→```
   359→
   360→Domain tables:
   361→
   362→``` text
   363→poultry_flocks
   364→poultry_farms
   365→restaurant_orders
   366→retail_products
   367→```
   368→
   369→Core should not own domain-specific business rules.
   370→
   371→------------------------------------------------------------------------
   372→
   373→# 14. Tenant Isolation Model
   374→
   375→Primary model:
   376→
   377→``` text
   378→organization_id
   379→```
   380→
   381→Every tenant-owned table should either:
   382→
   383→1.  contain `organization_id`, or
   384→2.  have an unambiguous foreign-key path to a table containing
   385→    `organization_id`.
   386→
   387→For high-risk tables, direct organization ownership is preferred.
   388→
   389→------------------------------------------------------------------------
   390→
   391→# 15. Tenant Isolation Enforcement
   392→
   393→Use multiple layers:
   394→
   395→``` text
   396→Frontend
   397→ ↓
   398→API Authorization
   399→ ↓
   400→Service Authorization
   401→ ↓
   402→Data Access Layer
   403→ ↓
   404→PostgreSQL RLS
   405→```
   406→
   407→No single layer should be considered the only protection.
   408→
   409→Supabase's current guidance explicitly recommends RLS for exposed tables
   410→and emphasizes that grants and RLS are separate controls: grants
   411→determine whether a role can reach an object, while RLS determines which
   412→rows are accessible. citeturn0search12turn0search0
   413→
   414→------------------------------------------------------------------------
   415→
   416→# 16. RLS Strategy
   417→
   418→For tables exposed through a client-facing Data API:
   419→
   420→``` text
   421→Enable RLS
   422→+
   423→Create explicit policies
   424→+
   425→Grant least privilege
   426→```
   427→
   428→Supabase currently recommends enabling RLS on tables in exposed schemas
   429→and using policies for row-level authorization.
   430→citeturn0search0turn0search12
   431→
   432→------------------------------------------------------------------------
   433→
   434→# 17. RLS Policy Model
   435→
   436→Conceptually:
   437→
   438→``` text
   439→Authenticated User
   440→       ↓
   441→Organization Membership
   442→       ↓
   443→Organization ID
   444→       ↓
   445→Allowed Resource
   446→```
   447→
   448→Example policy logic:
   449→
   450→``` text
   451→user belongs to organization
   452→AND
   453→row.organization_id = organization
   454→```
   455→
   456→Do not use authentication alone as authorization.
   457→
   458→------------------------------------------------------------------------
   459→
   460→# 18. RLS and UPDATE
   461→
   462→Update authorization must check both:
   463→
   464→``` text
   465→existing row access
   466→+
   467→new row ownership
   468→```
   469→
   470→In PostgreSQL RLS this means using appropriate `USING` and `WITH CHECK`
   471→conditions for updates. Supabase's current RLS guidance explicitly calls
   472→this out. citeturn0search0
   473→
   474→------------------------------------------------------------------------
   475→
   476→# 19. Authorization Data
   477→
   478→Authorization data should come from trusted sources.
   479→
   480→Do not use user-editable profile metadata as the authoritative source
   481→for authorization.
   482→
   483→Supabase specifically warns that user-editable `raw_user_meta_data`
   484→should not be used for authorization decisions; authorization metadata
   485→belongs in trusted application-level data. citeturn18file0
   486→
   487→------------------------------------------------------------------------
   488→
   489→# 20. Service-Level Access
   490→
   491→Backend services may need elevated access for trusted operations.
   492→
   493→Rules:
   494→
   495→``` text
   496→Service access
   497→≠
   498→frontend access
   499→```
   500→
   501→Secrets and service credentials must remain server-side.
   502→
   503→Supabase documents that service-role/secret keys bypass RLS and
   504→therefore must never be exposed in frontend applications.
   505→citeturn0search11
   506→
   507→------------------------------------------------------------------------
   508→
   509→# 21. Database Schema Organization
   510→
   511→Recommended logical grouping:
   512→
   513→``` text
   514→core
   515→identity
   516→billing
   517→audit
   518→integration
   519→ai
   520→analytics
   521→poultry
   522→restaurant
   523→retail
   524→```
   525→
   526→Whether these become PostgreSQL schemas or naming conventions is an
   527→implementation decision, but ownership must remain explicit.
   528→
   529→------------------------------------------------------------------------
   530→
   531→# 22. IDs
   532→
   533→Use globally unique identifiers.
   534→
   535→Recommended default:
   536→
   537→``` text
   538→UUID
   539→```
   540→
   541→or another collision-resistant identifier strategy.
   542→
   543→Avoid exposing sequential database IDs where they create unnecessary
   544→enumeration risk.
   545→
   546→------------------------------------------------------------------------
   547→
   548→# 23. Foreign Keys
   549→
   550→Use foreign keys for important relational integrity.
   551→
   552→Examples:
   553→
   554→``` text
   555→organization_members.organization_id
   556→→ organizations.id
   557→
   558→poultry_flocks.organization_id
   559→→ organizations.id
   560→```
   561→
   562→Do not rely only on application code for critical referential integrity.
   563→
   564→------------------------------------------------------------------------
   565→
   566→# 24. Delete Strategy
   567→
   568→Do not blindly cascade-delete business data.
   569→
   570→Define per entity:
   571→
   572→``` text
   573→hard delete
   574→soft delete
   575→archive
   576→retention
   577→anonymization
   578→```
   579→
   580→Financial/audit records may require different lifecycle rules from
   581→temporary operational data.
   582→
   583→------------------------------------------------------------------------
   584→
   585→# 25. Timestamps
   586→
   587→Important tables should normally include:
   588→
   589→``` text
   590→created_at
   591→updated_at
   592→```
   593→
   594→Additional lifecycle timestamps may include:
   595→
   596→``` text
   597→deleted_at
   598→archived_at
   599→activated_at
   600→completed_at
   601→```
   602→
   603→Store timestamps consistently in UTC at the persistence layer.
   604→
   605→------------------------------------------------------------------------
   606→
   607→# 26. Concurrency
   608→
   609→Critical business updates should use appropriate concurrency controls.
   610→
   611→Options:
   612→
   613→``` text
   614→transactions
   615→row locks
   616→optimistic versioning
   617→unique constraints
   618→idempotency
   619→```
   620→
   621→Example:
   622→
   623→``` text
   624→inventory update
   625→+
   626→concurrent order
   627→```
   628→
   629→must not silently produce impossible inventory state.
   630→
   631→------------------------------------------------------------------------
   632→
   633→# 27. Transactions
   634→
   635→Use transactions for atomic business changes.
   636→
   637→Example:
   638→
   639→``` text
   640→Create Purchase Request
   641→+
   642→Create Audit Record
   643→+
   644→Create Outbox Event
   645→```
   646→
   647→All can be committed atomically where appropriate.
   648→
   649→------------------------------------------------------------------------
   650→
   651→# 28. JSONB
   652→
   653→JSONB is allowed for:
   654→
   655→``` text
   656→flexible configuration
   657→provider payloads
   658→domain-specific metadata
   659→integration settings
   660→AI metadata
   661→```
   662→
   663→Do not use JSONB as an excuse to avoid modeling stable relational
   664→fields.
   665→
   666→------------------------------------------------------------------------
   667→
   668→# 29. Database Constraints
   669→
   670→Use database constraints for invariants.
   671→
   672→Examples:
   673→
   674→``` text
   675→NOT NULL
   676→UNIQUE
   677→CHECK
   678→FOREIGN KEY
   679→```
   680→
   681→Business invariants that must never be violated should be enforced as
   682→close to the data as practical.
   683→
   684→------------------------------------------------------------------------
   685→
   686→# 30. Indexing
   687→
   688→Index based on actual query patterns.
   689→
   690→Common multi-tenant index:
   691→
   692→``` text
   693→(organization_id, created_at)
   694→```
   695→
   696→Domain examples:
   697→
   698→``` text
   699→(organization_id, farm_id)
   700→(organization_id, status)
   701→(organization_id, branch_id, created_at)
   702→```
   703→
   704→Do not create indexes for every column.
   705→
   706→------------------------------------------------------------------------
   707→
   708→# 31. RLS Performance
   709→
   710→RLS can affect query performance, especially on large tables.
   711→
   712→Design policies and indexes together.
   713→
   714→Supabase's current documentation specifically recommends indexing
   715→columns used by RLS policies and optimizing policy expressions for
   716→performance. citeturn0search0
   717→
   718→------------------------------------------------------------------------
   719→
   720→# 32. Partitioning
   721→
   722→Partition only when data volume and access patterns justify it.
   723→
   724→Potential candidates:
   725→
   726→``` text
   727→high-volume events
   728→telemetry
   729→audit history
   730→transaction history
   731→large time-series data
   732→```
   733→
   734→Partition keys might include:
   735→
   736→``` text
   737→time
   738→organization
   739→domain
   740→```
   741→
   742→Do not partition every table prematurely.
   743→
   744→------------------------------------------------------------------------
   745→
   746→# 33. Read Scaling
   747→
   748→As demand grows:
   749→
   750→``` text
   751→Primary
   752→ ↓
   753→Read Replicas
   754→ ↓
   755→Analytics / Warehouse
   756→```
   757→
   758→Transactional writes remain on the authoritative primary.
   759→
   760→------------------------------------------------------------------------
   761→
   762→# 34. Analytics Boundary
   763→
   764→Do not run heavy analytical workloads against the transactional database
   765→indefinitely.
   766→
   767→Architecture:
   768→
   769→``` text
   770→PostgreSQL
   771→ ↓
   772→CDC / ETL / Events
   773→ ↓
   774→Analytics Store / Warehouse
   775→```
   776→
   777→Operational dashboards may still use optimized transactional queries for
   778→low-volume needs.
   779→
   780→------------------------------------------------------------------------
   781→
   782→# 35. Redis
   783→
   784→Redis is not the source of truth.
   785→
   786→Use it for:
   787→
   788→``` text
   789→cache
   790→rate limiting
   791→short-lived sessions/state
   792→distributed coordination
   793→queue support
   794→temporary AI state
   795→```
   796→
   797→Never treat cached state as authoritative business records.
   798→
   799→------------------------------------------------------------------------
   800→
   801→# 36. Cache Rules
   802→
   803→Every cache should define:
   804→
   805→``` text
   806→key
   807→scope
   808→TTL
   809→invalidation
   810→fallback
   811→```
   812→
   813→Tenant-sensitive cache keys must include tenant scope where required.
   814→
   815→Example:
   816→
   817→``` text
   818→org:{organization_id}:dashboard:{period}
   819→```
   820→
   821→------------------------------------------------------------------------
   822→
   823→# 37. Object Storage
   824→
   825→Store large binary objects outside PostgreSQL.
   826→
   827→Examples:
   828→
   829→``` text
   830→images
   831→documents
   832→PDFs
   833→exports
   834→attachments
   835→AI artifacts
   836→```
   837→
   838→Database stores metadata and secure object references.
   839→
   840→------------------------------------------------------------------------
   841→
   842→# 38. Object Storage Isolation
   843→
   844→Object paths should be tenant-aware.
   845→
   846→Example:
   847→
   848→``` text
   849→organizations/{org_id}/documents/{object_id}
   850→```
   851→
   852→Access should be controlled with:
   853→
   854→``` text
   855→authorization
   856→signed URLs
   857→expiry
   858→object policies
   859→```
   860→
   861→------------------------------------------------------------------------
   862→
   863→# 39. Search
   864→
   865→Search architecture may combine:
   866→
   867→``` text
   868→PostgreSQL full-text search
   869→+
   870→dedicated search engine where justified
   871→```
   872→
   873→Start with PostgreSQL where it is sufficient.
   874→
   875→Do not introduce another search system without a real workload
   876→requirement.
   877→
   878→------------------------------------------------------------------------
   879→
   880→# 40. Vector Data
   881→
   882→Mianx AI may use vector embeddings for:
   883→
   884→``` text
   885→knowledge retrieval
   886→semantic search
   887→memory retrieval
   888→document search
   889→```
   890→
   891→PostgreSQL with pgvector is an appropriate initial option where the
   892→workload fits.
   893→
   894→Supabase currently supports `pgvector` as a Postgres extension; current
   895→platform guidance also notes that explicit extension version pinning is
   896→deprecated in favor of the platform's default extension versions.
   897→citeturn0search1turn0search13
   898→
   899→------------------------------------------------------------------------
   900→
   901→# 41. Vector Isolation
   902→
   903→Every vector record must preserve authorization scope.
   904→
   905→Conceptually:
   906→
   907→``` text
   908→embedding
   909→ ├── organization_id
   910→ ├── domain
   911→ ├── source_id
   912→ ├── visibility
   913→ └── embedding
   914→```
   915→
   916→Similarity search must apply tenant/domain filters before returning
   917→usable context.
   918→
   919→------------------------------------------------------------------------
   920→
   921→# 42. AI Memory Storage
   922→
   923→Memory should be separated logically into:
   924→
   925→``` text
   926→session
   927→conversation
   928→user
   929→organization
   930→domain
   931→agent
   932→```
   933→
   934→Each record should include scope and ownership metadata.
   935→
   936→------------------------------------------------------------------------
   937→
   938→# 43. AI Knowledge Storage
   939→
   940→Knowledge records should preserve:
   941→
   942→``` text
   943→source
   944→organization
   945→domain
   946→document
   947→version
   948→visibility
   949→chunk
   950→embedding
   951→metadata
   952→```
   953→
   954→The model should be able to trace important answers back to authorized
   955→sources.
   956→
   957→------------------------------------------------------------------------
   958→
   959→# 44. AI Data Retention
   960→
   961→Define separate retention policies for:
   962→
   963→``` text
   964→conversation history
   965→agent runs
   966→tool calls
   967→memory
   968→knowledge documents
   969→embeddings
   970→AI cost telemetry
   971→```
   972→
   973→Do not retain everything forever by default.
   974→
   975→------------------------------------------------------------------------
   976→
   977→# 45. Audit Data
   978→
   979→Audit logs are separate from ordinary application logs.
   980→
   981→Audit records should capture important:
   982→
   983→``` text
   984→actor
   985→organization
   986→action
   987→resource
   988→before/after where appropriate
   989→timestamp
   990→request_id
   991→```
   992→
   993→Audit records should have controlled retention and access.
   994→
   995→------------------------------------------------------------------------
   996→
   997→# 46. Sensitive Data
   998→
   999→Classify data:
  1000→
  1001→``` text
  1002→Public
  1003→Internal
  1004→Confidential
  1005→Restricted
  1006→```
  1007→
  1008→Restricted information may include:
  1009→
  1010→``` text
  1011→credentials
  1012→financial secrets
  1013→private customer information
  1014→security material
  1015→tokens
  1016→```
  1017→
  1018→Sensitive values must not appear in ordinary logs.
  1019→
  1020→------------------------------------------------------------------------
  1021→
  1022→# 47. Secrets
  1023→
  1024→Secrets belong in a secrets-management system, not normal business
  1025→tables.
  1026→
  1027→Examples:
  1028→
  1029→``` text
  1030→API keys
  1031→OAuth refresh tokens
  1032→database credentials
  1033→encryption keys
  1034→webhook secrets
  1035→```
  1036→
  1037→Applications should retrieve secrets securely at runtime.
  1038→
  1039→------------------------------------------------------------------------
  1040→
  1041→# 48. Encryption
  1042→
  1043→Use encryption:
  1044→
  1045→``` text
  1046→in transit
  1047→at rest
  1048→```
  1049→
  1050→For highly sensitive application fields, consider application-level
  1051→encryption where justified.
  1052→
  1053→Key management must be separate from encrypted data.
  1054→
  1055→------------------------------------------------------------------------
  1056→
  1057→# 49. Database Backups
  1058→
  1059→Backups should be:
  1060→
  1061→``` text
  1062→automated
  1063→monitored
  1064→tested
  1065→retained
  1066→protected
  1067→```
  1068→
  1069→A backup that has never been restored is not a proven recovery
  1070→mechanism.
  1071→
  1072→Supabase documents daily database backups and point-in-time recovery on
  1073→paid plans; however, storage objects are not included in database
  1074→backups, so object-storage backup strategy must be handled separately.
  1075→citeturn0search1
  1076→
  1077→------------------------------------------------------------------------
  1078→
  1079→# 50. Disaster Recovery
  1080→
  1081→Define:
  1082→
  1083→``` text
  1084→RPO
  1085→RTO
  1086→backup frequency
  1087→restore procedure
  1088→failover strategy
  1089→regional recovery
  1090→```
  1091→
  1092→Different data classes may have different targets.
  1093→
  1094→------------------------------------------------------------------------
  1095→
  1096→# 51. Restore Testing
  1097→
  1098→At planned intervals:
  1099→
  1100→``` text
  1101→Backup
  1102→ ↓
  1103→Restore
  1104→ ↓
  1105→Integrity checks
  1106→ ↓
  1107→Application verification
  1108→ ↓
  1109→Document result
  1110→```

  1112→Recovery testing belongs in the production operations process.

  1114→------------------------------------------------------------------------
  1115→
  1116→# 52. Migration Strategy
  1117→
  1118→All production schema changes should be migration-controlled.
  1119→
  1120→Process:
  1121→
  1122→``` text
  1123→Migration
  1124→ ↓
  1125→Review
  1126→ ↓
  1127→Test
  1128→ ↓
  1129→Staging
  1130→ ↓
  1131→Production
  1132→```
  1133→
  1134→Avoid manual production schema changes that cannot be reproduced.
  1135→
  1136→------------------------------------------------------------------------
  1137→
  1138→# 53. Expand / Contract Migrations
  1139→
  1140→For risky changes:
  1141→
  1142→``` text
  1143→Expand
  1144→ ↓
  1145→Deploy compatible code
  1146→ ↓
  1147→Backfill
  1148→ ↓
  1149→Switch reads/writes
  1150→ ↓
  1151→Contract
  1152→```
  1153→
  1154→This avoids downtime from incompatible schema changes.
  1155→
  1156→------------------------------------------------------------------------
  1157→
  1158→# 54. Data Backfills
  1159→
  1160→Large backfills should be:
  1161→
  1162→``` text
  1163→batched
  1164→resumable
  1165→observable
  1166→rate-limited
  1167→idempotent
  1168→```
  1169→
